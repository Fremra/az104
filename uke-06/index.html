Del A — App Service (ca. 30 min)

1. Web app i Bicep

Hvorfor: en web-app er to ressurser: planen, som er maskinene (se uke 5, steg 10), og selve appen, som kjører på dem. Deployment Center er stedet der du kobler appen til koden, med GitHub, Bitbucket, Azure Repos eller lokal Git som kilde. Vi laster opp en zip-fil direkte, så vi slipper å sette opp et repo. Siden skriver ut en connection string og en app setting, så du kan se hva en swap gjør i steg 2.

Oppgave: lag rg-uke06 i Sweden Central, og deploy fila under. Åpne web-appen, og se under Deployment → Deployment Center hvilke kilder du kan velge, uten å lagre. Gå så til Settings → Environment variables. Under Connection strings legger du til DB med verdien database-1 og typen Custom. Under App settings legger du til MILJO med verdien produksjon og krysser av for Deployment slot setting. Last så opp koden, og åpne adressen under Overview. 

@'
@description('Navnet på web-appen. Må være unikt i hele Azure')
param appName string

@description('Tieren til App Service-planen. Slots og autoscale krever Standard eller høyere')
param sku string = 'S1'

resource plan 'Microsoft.Web/serverfarms@2024-04-01' = {
  name: 'plan-uke06'
  location: resourceGroup().location
  kind: 'linux'
  sku: {
    name: sku
    capacity: 1
  }
  properties: {
    reserved: true
  }
}

resource app 'Microsoft.Web/sites@2024-04-01' = {
  name: appName
  location: resourceGroup().location
  kind: 'app,linux'
  properties: {
    serverFarmId: plan.id
    siteConfig: {
      linuxFxVersion: 'PHP|8.4'
    }
  }
}

output url string = 'https://${app.properties.defaultHostName}'
'@ | Set-Content main.bicep -Encoding utf8
az group create --name $RG --location $L --query properties.provisioningState -o tsv
az deployment group create -g $RG --name app --template-file main.bicep --parameters appName=$APP `
  --query properties.outputs.url.value -o tsv

Koden lager du og laster opp slik. Første opplasting tok tre minutter i testen, fordi appen må starte.

'<?php echo "Versjon 1 | DB=" . getenv("CUSTOMCONNSTR_DB") . " | MILJO=" . getenv("MILJO");' | Set-Content index.php -Encoding ascii
Compress-Archive -Path index.php -DestinationPath v1.zip -Force
az webapp deploy -g $RG -n $APP --src-path v1.zip --type zip -o none

Siden skal vise Versjon 1 | DB=database-1 | MILJO=produksjon. Connection strings kommer inn i appen som miljøvariabler med et prefiks etter typen, her CUSTOMCONNSTR_.

Vis kommando
az webapp config connection-string set -g $RG -n $APP -t Custom --settings DB=database-1 -o none
az webapp config appsettings set -g $RG -n $APP --slot-settings MILJO=produksjon -o none

2. Deployment slots og swap

Hvorfor: en deployment slot er en egen kopi av appen med egen adresse, på samme plan. Du tester den nye versjonen i staging og bytter den inn i produksjon med en swap, og du kommer tilbake ved å swappe igjen. Slots krever Standard (5 slots) eller Premium (20). Koden flytter seg alltid. De fleste innstillingene følger med, også connection strings, med mindre de er merket Deployment slot setting. Custom domains, scale settings, HTTPS Only og IP-regler følger aldri med. Eksamen spør hva som flytter seg og hva som blir igjen.

Oppgave: åpne Deployment → Deployment slots, og legg til staging med innstillingene klonet fra produksjonsappen. Åpne Environment variables på slotten, og se at DB ble klonet, men ikke MILJO. Endre DB til database-2, og legg til MILJO med verdien staging og Deployment slot setting. Last opp versjon 2 til slotten med kommandoene under. Sammenlign de to adressene, trykk Swap, og sammenlign igjen. Swappen tok to–tre minutter i testen. 

'<?php echo "Versjon 2 | DB=" . getenv("CUSTOMCONNSTR_DB") . " | MILJO=" . getenv("MILJO");' | Set-Content index.php -Encoding ascii
Compress-Archive -Path index.php -DestinationPath v2.zip -Force
az webapp deploy -g $RG -n $APP --slot staging --src-path v2.zip --type zip -o none

Etter swappen skal produksjon vise Versjon 2 | DB=database-2 | MILJO=produksjon. Koden og connection stringen flyttet seg, men MILJO ble igjen.

Vis kommando
az webapp deployment slot create -g $RG -n $APP --slot staging --configuration-source $APP --query name -o tsv
az webapp config connection-string set -g $RG -n $APP --slot staging -t Custom --settings DB=database-2 -o none
az webapp config appsettings set -g $RG -n $APP --slot staging --slot-settings MILJO=staging -o none
az webapp deployment slot swap -g $RG -n $APP --slot staging --target-slot production -o none
Invoke-RestMethod "https://$APP.azurewebsites.net"
Invoke-RestMethod "https://$APP-staging.azurewebsites.net"

3. TLS og custom domain

Hvorfor: HTTPS Only sender all HTTP-trafikk videre til HTTPS, og minimum TLS er 1.2 som standard. Et eget domene krever to DNS-poster: en CNAME (eller en A-post for rotdomenet) som peker på appen, og en TXT-post asuid som beviser at domenet er ditt. Free-tieren kan ikke ha custom domain. Azures gratis managed certificate krever Basic eller høyere og et custom domain, og det støtter ikke wildcard. Vi har ikke noe domene å bruke, så her ser vi bare på dialogen.

Oppgave: sett HTTPS Only til On under Settings → Configuration → General settings, og se hva minimum TLS står på. Åpne http://-adressen til appen, og se at du havner på https://. Slotten har sin egen innstilling, så der står HTTPS Only fortsatt av. Åpne Settings → Custom domains → Add custom domain, skriv inn et domene du finner på, og se hvilke poster dialogen ber om. Avbryt.

Vis kommando
az webapp update -g $RG -n $APP --https-only true --query httpsOnly -o tsv
az webapp show -g $RG -n $APP --slot staging --query httpsOnly -o tsv
az webapp config show -g $RG -n $APP --query minTlsVersion -o tsv
az webapp config hostname add -g $RG --webapp-name $APP --hostname www.eksempel.no      # feiler: TXT-posten mangler

4. Backup

Hvorfor: App Service har to typer backup, og begge krever Basic eller høyere. Automatisk backup krever ikke oppsett, går hver time og tas vare på i 30 dager, men kan ikke lastes ned. Custom backup legges i en storage account du velger, kan lastes ned og er på høyst 10 GB. Storage accounten må ligge i samme subscription, og den kan ikke stå bak en brannmur.

Oppgave: åpne Settings → Backups. En ny app har ingen automatiske backuper ennå. Lag en storage account med navnet i $ST og en container backup. Sett opp custom backup i appen mot containeren, og kjør en backup. Se at filene dukker opp i containeren. Backupen tok under halvannet minutt i testen.

Vis kommando
az storage account create -g $RG -n $ST -l $L --sku Standard_LRS --query provisioningState -o tsv
$KEY = az storage account keys list -g $RG -n $ST --query "[0].value" -o tsv
az storage container create --account-name $ST --account-key $KEY -n backup -o none
$SLUTT = (Get-Date).ToUniversalTime().AddDays(1).ToString("yyyy-MM-ddTHH:mmZ")
$SAS = az storage container generate-sas --account-name $ST --account-key $KEY -n backup --permissions rwdl --expiry $SLUTT -o tsv
$URL = "https://$ST.blob.core.windows.net/backup?$SAS"
az webapp config backup create -g $RG --webapp-name $APP --backup-name manuell --container-url "`"$URL`"" -o none      # lokalt
az webapp config backup create -g $RG --webapp-name $APP --backup-name manuell --container-url $URL -o none      # Cloud Shell
az webapp config backup list -g $RG --webapp-name $APP --query "[].{navn:name, status:status}" -o table
az storage blob list --account-name $ST --account-key $KEY -c backup --query "[].name" -o tsv

Lokalt må adressen ha ekstra anførselstegn, fordi den inneholder &.

5. Nettverk

Hvorfor: nettverk for App Service deles i inn og ut. Inn styres av access restrictions (IP-regler, høyst 512) og private endpoints. Ut styres av VNet integration, som lar appen nå ressurser i et VNet. Subnettet må stå i samme region, være delegert til Microsoft.Web/serverFarms og være minst /28 (/27 hvis portalen lager det). Private endpoints tar vi i uke 7.

Oppgave: åpne Settings → Networking, og legg til en Allow-regel for 203.0.113.0/24 under tilgangsreglene. Det er ikke din IP, og reglene ender med en Deny for alle andre. Åpne appen (403) og slotten (virker, reglene følger ikke med). Fjern regelen. Lag så VNet-et vnet-uke06 med subnettet app på 10.6.0.0/28, og koble appen til det under Virtual network integration.

Vis kommando
az webapp config access-restriction add -g $RG -n $APP --rule-name bare-test --action Allow --ip-address 203.0.113.0/24 --priority 100 -o none
az webapp config access-restriction show -g $RG -n $APP --query "ipSecurityRestrictions[].{navn:name, handling:action, ip:ipAddress}" -o table
az webapp config access-restriction remove -g $RG -n $APP --rule-name bare-test -o none
az network vnet create -g $RG -n vnet-uke06 -l $L --address-prefixes 10.6.0.0/16 --subnet-name app --subnet-prefixes 10.6.0.0/28 -o none
az network vnet subnet update -g $RG --vnet-name vnet-uke06 -n app --delegations Microsoft.Web/serverFarms -o none
az webapp vnet-integration add -g $RG -n $APP --vnet vnet-uke06 --subnet app -o none
az webapp vnet-integration list -g $RG -n $APP --query "[].name" -o tsv

6. Autoscale

Hvorfor: autoscale settes på planen, ikke på appen, så alle appene og slottene i planen skalerer sammen. Regel-basert autoscale krever Standard eller høyere og virker som i uke 5, steg 9. Automatic scaling er en annen metode, der plattformen bestemmer selv, og den krever Premium.

Oppgave: åpne Settings → Scale out og velg Rules Based. Lag en custom autoscale med minimum 2, maksimum 3 og standard 2. Legg til en regel som legger til én instans når CPU er over 70 % i snitt i 5 minutter, og en som fjerner én når den er under 30 %. Lagre. Planen står på 1 instans, som er under minimum, så den går til 2 av seg selv. Det tok under tre minutter i testen. Se det under Run history.

Vis kommando
$PLAN = az appservice plan show -g $RG -n plan-uke06 --query id -o tsv
az monitor autoscale create -g $RG --resource $PLAN --name skaler-plan --min-count 2 --max-count 3 --count 2 -o none
az monitor autoscale rule create -g $RG --autoscale-name skaler-plan --condition "CpuPercentage > 70 avg 5m" --scale out 1 -o none
az monitor autoscale rule create -g $RG --autoscale-name skaler-plan --condition "CpuPercentage < 30 avg 5m" --scale in 1 -o none
az appservice plan show -g $RG -n plan-uke06 --query sku.capacity -o tsv      # kjør igjen etter noen minutter

Del B — Containere (ca. 25 min)

7. Container Registry

Hvorfor: et registry er der du lagrer dine egne images. Tierene er Basic, Standard og Premium, og bare Premium har geo-replikering og private endpoints. az acr build bygger imaget i Azure, så du trenger ikke Docker på maskinen, og resultatet er det samme som med docker build og docker push. az acr import kopierer et ferdig image fra et annet registry.

Oppgave: lag et registry i Basic med navnet i $ACR. Lag de to filene under, og bygg imaget. Importer så aci-helloworld, og se begge under Repositories. Slå på Admin user under Access keys. Den er av som standard, og vi trenger den for å hente imaget i steg 8. Den gir full tilgang, så i ekte miljøer bruker du heller en managed identity med rollen AcrPull. 

az acr create -g $RG -n $ACR --sku Basic --query loginServer -o tsv
'<h1>Versjon 1</h1>' | Set-Content index.html -Encoding ascii
@'
FROM mcr.microsoft.com/azurelinux/base/nginx:1.25
COPY index.html /usr/share/nginx/html/index.html
'@ | Set-Content Dockerfile -Encoding ascii
az acr build -r $ACR -t web:v1 . --no-logs --query status -o tsv
Vis kommando
az acr import -n $ACR --source mcr.microsoft.com/azuredocs/aci-helloworld:latest --image aci-helloworld:v1
az acr repository list -n $ACR -o tsv
az acr update -n $ACR --admin-enabled true --query adminUserEnabled -o tsv

8. Container Instances

Hvorfor: ACI er den enkleste måten å kjøre en container på, uten VM og uten orkestrering. Den starter raskt, og du betaler for tiden den kjører. Du velger CPU og minne når den lages, og de kan ikke endres etterpå. ACI skalerer heller ikke av seg selv. En container deler kjernen med verten, så trenger du full isolasjon, må du ha en VM.

Oppgave: lag aci-web med Create → Container Instance: imaget web:v1 fra registryet ditt, 1 vCPU og 1 GiB. Sett DNS-navnet aci-uke06- og verdien av $ID under Networking. Åpne adressen under Overview, og se loggene under Containers. Prøv så å endre CPU med kommandoen under. Det går ikke uten å slette container groupen og lage den på nytt. 

$ACRPASS = az acr credential show -n $ACR --query "passwords[0].value" -o tsv
Vis kommando
az container create -g $RG -n aci-web --image "$ACR.azurecr.io/web:v1" --registry-login-server "$ACR.azurecr.io" `
  --registry-username $ACR --registry-password $ACRPASS --os-type Linux --cpu 1 --memory 1 --ports 80 `
  --dns-name-label "aci-uke06-$ID" -o none
az container show -g $RG -n aci-web --query ipAddress.fqdn -o tsv
az container logs -g $RG -n aci-web
az container create -g $RG -n aci-web --image "$ACR.azurecr.io/web:v1" --registry-login-server "$ACR.azurecr.io" `
  --registry-username $ACR --registry-password $ACRPASS --os-type Linux --cpu 2 --memory 1 --ports 80 `
  --dns-name-label "aci-uke06-$ID" -o none      # feiler

9. Container group og restart policy

Hvorfor: en container group er flere containere på samme vert. De deler IP, porter, livssyklus og lagring, så de når hverandre på localhost, og ressursene legges sammen. Flere containere i en gruppe lager du med Bicep, ARM eller YAML. Restart policy bestemmer hva som skjer når prosessen stopper: Always starter alltid på nytt, OnFailure bare ved feil, og Never lar den stå stoppet. De to siste passer til jobber som skal bli ferdige.

Oppgave: deploy fila under. Se de to containerne under Containers, og se i loggen at sidecar får svar fra web på localhost. Den første linjen kan være en feil, hvis web ikke har startet ennå. Lag så to kortvarige containere, og sammenlign. Den ene stopper og blir stående, den andre startes på nytt igjen og igjen. 

@'
@description('DNS-navnet til container groupen. Må være unikt i regionen')
param dnsLabel string

@allowed([ 'Always', 'OnFailure', 'Never' ])
@description('Hva Azure gjør når en container stopper')
param restartPolicy string = 'OnFailure'

resource gruppe 'Microsoft.ContainerInstance/containerGroups@2023-05-01' = {
  name: 'aci-gruppe'
  location: resourceGroup().location
  properties: {
    osType: 'Linux'
    restartPolicy: restartPolicy
    ipAddress: {
      type: 'Public'
      dnsNameLabel: dnsLabel
      ports: [
        {
          port: 80
          protocol: 'TCP'
        }
      ]
    }
    containers: [
      {
        name: 'web'
        properties: {
          image: 'mcr.microsoft.com/azuredocs/aci-helloworld:latest'
          ports: [
            {
              port: 80
              protocol: 'TCP'
            }
          ]
          resources: {
            requests: {
              cpu: 1
              memoryInGB: 1
            }
          }
        }
      }
      {
        name: 'sidecar'
        properties: {
          image: 'mcr.microsoft.com/azurelinux/busybox:1.36'
          command: [
            'sh'
            '-c'
            'while true; do wget -q -O - http://localhost:80 | grep -o "Welcome to Azure Container Instances"; sleep 30; done'
          ]
          resources: {
            requests: {
              cpu: json('0.5')
              memoryInGB: json('0.5')
            }
          }
        }
      }
    ]
  }
}

output fqdn string = gruppe.properties.ipAddress.fqdn
'@ | Set-Content aci.bicep -Encoding utf8
az deployment group create -g $RG --name aci --template-file aci.bicep --parameters dnsLabel="aci-gruppe-$ID" `
  --query properties.outputs.fqdn.value -o tsv
az container logs -g $RG -n aci-gruppe --container-name sidecar
az container create -g $RG -n aci-jobb --image mcr.microsoft.com/azurelinux/busybox:1.36 --os-type Linux --cpu 1 --memory 1 `
  --restart-policy Never --command-line "sh -c 'echo Ferdig; exit 0'" -o none
az container create -g $RG -n aci-feil --image mcr.microsoft.com/azurelinux/busybox:1.36 --os-type Linux --cpu 1 --memory 1 `
  --restart-policy OnFailure --command-line "sh -c 'echo Feilet; exit 1'" -o none

Vent et minutt, og se tilstanden og hvor mange ganger de har startet på nytt:

"aci-jobb","aci-feil" | ForEach-Object {
  az container show -g $RG -n $_ --query "containers[0].instanceView.{tilstand:currentState.state, omstarter:restartCount}" -o json
}

10. Container Apps

Hvorfor: Container Apps står mellom ACI og AKS. ACI passer til enkle, isolerte oppgaver, og AKS gir full kontroll over Kubernetes. Container Apps er serverless med orkestrering: skalering, revisions og ingress er innebygd, uten at du ser Kubernetes. Appene ligger i et environment. Skalering styres av regler for HTTP, TCP eller andre hendelser, og standard er 0 til 10 replicas. Står appen på 0, koster den ingen kjøretid.

Oppgave: lag ca-web med Create → Container App og et nytt environment env-uke06. Environmentet tok over to minutter i testen. Velg imaget web:v1 fra registryet ditt, ingress fra hvor som helst og målport 80. Sett min 0 og maks 3 replicas under Scale, og legg til en HTTP-regel på 10 samtidige forespørsler. Åpne adressen under Overview. Uten trafikk går appen til 0 replicas etter rundt fem minutter, og neste forespørsel vekker den. Se det under Revisions and replicas.

Vis kommando
az containerapp env create -g $RG -n env-uke06 -l $L -o none
$CA = az containerapp create -g $RG -n ca-web --environment env-uke06 --image "$ACR.azurecr.io/web:v1" `
  --registry-server "$ACR.azurecr.io" --registry-username $ACR --registry-password $ACRPASS `
  --ingress external --target-port 80 --min-replicas 0 --max-replicas 3 `
  --scale-rule-name http --scale-rule-type http --scale-rule-http-concurrency 10 `
  --query properties.configuration.ingress.fqdn -o tsv
(Invoke-WebRequest -UseBasicParsing "https://$CA").Content
az containerapp revision list -g $RG -n ca-web --query "[].{navn:name, replicas:properties.replicas}" -o table

11. Revisions og trafikkdeling

Hvorfor: en endring i selve containeren, som image, CPU eller skaleringsregler, lager en ny revision. Endringer i ingress og trafikkregler gjør det ikke. Med Multiple revision mode kan flere revisions kjøre samtidig, og du fordeler trafikken mellom dem. En ny revision får 0 % til du gir den trafikk.

Oppgave: bygg versjon 2 med kommandoene under. Sett revision mode til Multiple under Revisions and replicas, og lag en ny revision med web:v2 og suffikset v2. Fordel trafikken 80/20 på de to, og last siden på nytt noen ganger. 

'<h1>Versjon 2</h1>' | Set-Content index.html -Encoding ascii
az acr build -r $ACR -t web:v2 . --no-logs --query status -o tsv
Vis kommando
az containerapp revision set-mode -g $RG -n ca-web --mode multiple -o none
$REV1 = az containerapp revision list -g $RG -n ca-web --query "[0].name" -o tsv
az containerapp update -g $RG -n ca-web --image "$ACR.azurecr.io/web:v2" --revision-suffix v2 -o none
az containerapp ingress traffic set -g $RG -n ca-web --revision-weight "$REV1=80" "ca-web--v2=20" -o none
1..20 | ForEach-Object { (Invoke-WebRequest -UseBasicParsing "https://$CA").Content.Trim() } | Group-Object | Select-Object Count, Name

I testen ga 20 forespørsler 15 på versjon 1 og 5 på versjon 2.
