Del A — Virtuelle nettverk (ca. 20 min)

1. VNet, subnets og VM-er i Bicep

Hvorfor: et VNet er et privat nettverk i Azure, delt i subnets. Ressursene i det når hverandre, og med VPN eller ExpressRoute også nettverket on-prem. Planlegg adresserommet før du lager noe: VNet som skal peeres, kan ikke overlappe, og Azure tar fem adresser i hvert subnet. Nye VNet får nå private subnets, så en VM uten public IP kommer ikke ut på internett. Bicep-fila setter det eksplisitt med defaultOutboundAccess, så du ser innstillingen.

Oppgave: lag rg-uke07 i Sweden Central, og deploy fila under. Den lager vnet-app med subnettene web og db, vnet-hub med subnettet nva, og én VM i hvert subnet. VM-ene har ingen public IP og slår seg av kl. 20. Åpne vnet-app og Settings → Subnets, og se hvor mange ledige adresser et /24 har. Åpne db, og se at Enable private subnet er krysset av. Prøv så å legge til subnettet test med 10.7.2.0/25.

2. Public IP og privat IP

Hvorfor: en VM som skal nås fra internett, trenger en public IP. Standard er eneste SKU etter at Basic ble pensjonert i 2025. Adressen er alltid statisk, og den er stengt inn til en NSG åpner. Den gir også VM-en vei ut, og det er en av de eksplisitte måtene et private subnet krever. Private IP-er er dynamiske som standard. Statisk bruker du når andre skal peke på adressen, som en DNS-server eller en NVA.

Oppgave: lag public IP-en pip-web med SKU Standard. Koble den til vm-web-nic under Settings → IP configurations → ipconfig1. Sett den private IP-en på vm-db-nic til statisk 10.7.2.10 samme sted. Kjør så linja under på vm-web og vm-db med Operations → Run command → RunShellScript, og sammenlign. Hver run command tar rundt et halvt minutt. 

hostname -I; curl -s -m 5 https://ifconfig.me || echo ingen vei ut

vm-web skal vise public IP-en sin, og vm-db ingen vei ut. I testen fikk vm-db den nye adressen uten omstart.

Vis kommando
az network public-ip create -g $RG -n pip-web --sku Standard --allocation-method Static --query publicIp.ipAddress -o tsv
az network nic ip-config update -g $RG --nic-name vm-web-nic -n ipconfig1 --public-ip-address pip-web --query privateIPAllocationMethod -o tsv
az network nic ip-config update -g $RG --nic-name vm-db-nic -n ipconfig1 --private-ip-address 10.7.2.10 --query privateIPAllocationMethod -o tsv
"vm-web","vm-db" | ForEach-Object {
  az vm run-command invoke -g $RG -n $_ --command-id RunShellScript --scripts "hostname -I; curl -s -m 5 https://ifconfig.me || echo ingen vei ut" `
    --query "value[0].message" -o tsv
}

3. Peering

Hvorfor: peering kobler to VNet over Microsofts stamnett, med private IP-er og uten gateway. Det må lages fra begge sider, og status blir Connected når begge finnes. Peering er ikke transitiv: to spokes som er peeret med samme hub, når ikke hverandre uten en NVA eller gateway i huben. Global peering virker på samme måte mellom regioner. Har huben en VPN gateway, kan spokene bruke den med gateway transit: Allow gateway transit på huben og Use remote gateways på spoken.

Oppgave: åpne vnet-app og Settings → Peerings → Add. Velg vnet-hub, og kall peeringen app-til-hub på denne siden og hub-til-app på den andre. Kryss av for at vnet-app kan ta imot forwarded traffic fra vnet-hub. Det trenger vi i steg 4. Se statusen på begge VNet-ene, og kjør ping -c 2 10.70.1.4 på vm-web.

Vis kommando
az network vnet peering create -g $RG -n app-til-hub --vnet-name vnet-app --remote-vnet vnet-hub --allow-vnet-access `
  --allow-forwarded-traffic --query peeringState -o tsv
az network vnet peering create -g $RG -n hub-til-app --vnet-name vnet-hub --remote-vnet vnet-app --allow-vnet-access `
  --query peeringState -o tsv
az network vnet peering list -g $RG --vnet-name vnet-app --query "[].{navn:name, status:peeringState}" -o table
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "ping -c 2 10.70.1.4" --query "value[0].message" -o tsv

Den første svarer Initiated, fordi den andre siden mangler. Den andre svarer Connected.

4. User-defined routes

Hvorfor: Azure ruter av seg selv mellom subnets, til peerede VNet og ut på internett. Det er systemrutene. En route table med egne ruter overstyrer dem, og den mest spesifikke ruten vinner. Neste hopp kan være Virtual appliance, Virtual network gateway, Virtual network, Internet eller None. En virtual appliance (NVA) er typisk en brannmur i en hub. Den må ha IP forwarding både på NIC-en i Azure og i operativsystemet, ellers stopper trafikken der. Effective routes viser hvilke ruter som faktisk gjelder for en NIC, og er det første du sjekker når trafikken går feil vei.

Oppgave: slå på IP forwarding på vm-nva-nic under Settings → IP configurations, og i Linux med run command på vm-nva: sysctl -w net.ipv4.ip_forward=1. Lag route tablen rt-web med ruten til-db: 10.7.2.0/24 til Virtual appliance 10.70.1.4. Koble den til subnettet web under Settings → Subnets. Kjør tracepath -n -m 5 10.7.2.10 på vm-web. Se til slutt Help → Effective routes på vm-web-nic.

tracepath skal vise 10.70.1.4 før 10.7.2.10. Svaret går rett tilbake, fordi db ikke har noen route table.

Vis kommando
az network nic update -g $RG -n vm-nva-nic --ip-forwarding true --query enableIPForwarding -o tsv
az vm run-command invoke -g $RG -n vm-nva --command-id RunShellScript --scripts "sysctl -w net.ipv4.ip_forward=1" --query "value[0].message" -o tsv
az network route-table create -g $RG -n rt-web -l $L --query provisioningState -o tsv
az network route-table route create -g $RG --route-table-name rt-web -n til-db --address-prefix 10.7.2.0/24 `
  --next-hop-type VirtualAppliance --next-hop-ip-address 10.70.1.4 --query provisioningState -o tsv
az network vnet subnet update -g $RG --vnet-name vnet-app -n web --route-table rt-web --query routeTable.id -o tsv
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "tracepath -n -m 5 10.7.2.10" --query "value[0].message" -o tsv
az network nic show-effective-route-table -g $RG -n vm-web-nic `
  --query "value[?nextHopType!='None'].{kilde:source, prefiks:addressPrefix[0], neste:nextHopType, ip:nextHopIpAddress[0]}" -o table

Uten filteret får du også nesten hundre ruter med neste hopp None, som Azure legger inn av seg selv.

Del B — Sikker tilgang (ca. 30 min)

5. NSG og ASG

Hvorfor: en NSG er en liste med regler for trafikk inn og ut. Reglene sjekkes etter prioritet, lavest tall først, og den første som treffer, gjelder. En application security group (ASG) samler NIC-er etter funksjon, som web eller db. Reglene kan bruke ASG-en i stedet for IP-adresser, så en ny VM trenger bare å legges i gruppen. NIC-ene i en ASG må stå i samme VNet. Service tags som VirtualNetwork, Internet og Storage er ferdige adressegrupper som Microsoft holder ved like.

Oppgave: lag ASG-ene asg-web og asg-db, og legg vm-web og vm-db i hver sin under Networking → Application security groups. Lag NSG-en nsg-db, og koble den til subnettet db. Legg til to innkommende regler fra asg-web til asg-db på port 22: stopp-ssh-fra-web med Deny og prioritet 150, og tillat-ssh-fra-web med Allow og prioritet 200. Kjør nc -zv -w 3 10.7.2.10 22 på vm-web. Endre så prioriteten på deny-regelen til 250, og kjør igjen.

Vis kommando
az network asg create -g $RG -n asg-web -l $L --query provisioningState -o tsv
az network asg create -g $RG -n asg-db -l $L --query provisioningState -o tsv
az network nic ip-config update -g $RG --nic-name vm-web-nic -n ipconfig1 --application-security-groups asg-web -o none
az network nic ip-config update -g $RG --nic-name vm-db-nic -n ipconfig1 --application-security-groups asg-db -o none
az network nsg create -g $RG -n nsg-db -l $L --query NewNSG.provisioningState -o tsv
az network nsg rule create -g $RG --nsg-name nsg-db -n stopp-ssh-fra-web --priority 150 --access Deny --protocol Tcp `
  --source-asgs asg-web --destination-asgs asg-db --destination-port-ranges 22 --query provisioningState -o tsv
az network nsg rule create -g $RG --nsg-name nsg-db -n tillat-ssh-fra-web --priority 200 --access Allow --protocol Tcp `
  --source-asgs asg-web --destination-asgs asg-db --destination-port-ranges 22 --query provisioningState -o tsv
az network vnet subnet update -g $RG --vnet-name vnet-app -n db --nsg nsg-db --query networkSecurityGroup.id -o tsv
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "nc -zv -w 3 10.7.2.10 22" --query "value[0].message" -o tsv
az network nsg rule update -g $RG --nsg-name nsg-db -n stopp-ssh-fra-web --priority 250 --query priority -o tsv
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "nc -zv -w 3 10.7.2.10 22" --query "value[0].message" -o tsv

Med deny på 150 får du timed out. Med 250 får du succeeded.

6. Effective security rules

Hvorfor: en NSG kan stå på subnettet, på NIC-en eller på begge. Trafikk inn sjekkes mot subnettet først og så NIC-en, trafikk ut i motsatt rekkefølge, og den må slippe gjennom begge. Effective security rules viser alt som gjelder for en NIC, også standardreglene. De kan ikke slettes, men du kan overstyre dem med regler som har lavere tall.

Oppgave: åpne vm-db-nic og Help → Effective security rules. Finn regelen som stopper trafikk fra internett. Lag så NSG-en nsg-db-nic med regelen stopp-ssh: Deny, prioritet 100, kilde VirtualNetwork og port 22. Koble den til vm-db-nic under Settings → Network security group, og kjør nc fra steg 5 igjen. Se på effective security rules en gang til, og fjern så NSG-en fra NIC-en.

Vis kommando
az network nic list-effective-nsg -g $RG -n vm-db-nic `
  --query "value[].effectiveSecurityRules[?direction=='Inbound'].{navn:name, prioritet:priority, tilgang:access}[]" -o table
az network nsg create -g $RG -n nsg-db-nic -l $L --query NewNSG.provisioningState -o tsv
az network nsg rule create -g $RG --nsg-name nsg-db-nic -n stopp-ssh --priority 100 --access Deny --protocol Tcp `
  --source-address-prefixes VirtualNetwork --destination-port-ranges 22 --query provisioningState -o tsv
az network nic update -g $RG -n vm-db-nic --network-security-group nsg-db-nic --query networkSecurityGroup.id -o tsv
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "nc -zv -w 3 10.7.2.10 22" --query "value[0].message" -o tsv
az network nic list-effective-nsg -g $RG -n vm-db-nic --query "value[].networkSecurityGroup.id" -o tsv
az network nic update -g $RG -n vm-db-nic --remove networkSecurityGroup -o none

7. Bastion

Hvorfor: Bastion gir RDP og SSH i nettleseren over port 443, til VM-er som ikke har public IP. Developer er gratis, men den er delt, tar én tilkobling om gangen og når ikke VM-er i peerede VNet. Basic og høyere er dedikerte, krever et subnet som heter AzureBastionSubnet og er minst /26, og en Standard public IP. Basic koster 0,19 USD i timen i Sweden Central. Native client, altså SSH fra din egen terminal, krever Standard eller Premium.

Oppgave: åpne vm-db og Connect → Bastion, og velg å deploye Bastion Developer. Logg inn med azureuser og passordet i $PASSORD. Kjør hostname -I og curl -m 5 https://ifconfig.me i økten.

Vis kommando
az network bastion create -g $RG -n bas-uke07 -l $L --sku Developer --vnet-name vnet-app --query provisioningState -o tsv

Den var klar på sekunder i testen. Selve økten åpner du i portalen.

8. Service endpoint

Hvorfor: en service endpoint gir subnettet en egen vei til en Azure-tjeneste over stamnettet, og tjenesten ser hvilket subnet trafikken kommer fra. Da kan brannmuren på tjenesten slippe inn subnettet med en VNet-regel. Tjenesten har fortsatt public IP, og endepunktet er gratis. IP-regler virker ikke for trafikk fra samme region, så der trenger du en VNet-regel. Brannmuren kjenner du fra uke 4, steg 8.

Oppgave: lag en storage account med navnet i $ST. Under Security + networking → Networking slår du på tilgang bare fra valgte nettverk, og legger til vnet-app med subnettet db. Portalen slår på service endpointen for deg. Kjør linja under på vm-db og vm-web, med navnet ditt i stedet for stuke07xxxxxx. Prøv også lokalt med linja etter. 

curl -s -m 10 https://stuke07xxxxxx.blob.core.windows.net/?comp=list | grep -o -E 'AuthorizationFailure|PublicAccessNotPermitted' || echo ingen kontakt
try { Invoke-WebRequest -UseBasicParsing "https://$ST.blob.core.windows.net/?comp=list" } catch { $_.ErrorDetails.Message }

AuthorizationFailure betyr at brannmuren stoppet deg. PublicAccessNotPermitted betyr at du kom gjennom, men at anonym tilgang er av. Det holder, fordi vi tester nettverket. vm-db skal komme gjennom, mens vm-web og du lokalt skal bli stoppet.

Vis kommando
az storage account create -g $RG -n $ST -l $L --sku Standard_LRS --allow-blob-public-access false --query provisioningState -o tsv
az network vnet subnet update -g $RG --vnet-name vnet-app -n db --service-endpoints Microsoft.Storage --query "serviceEndpoints[].service" -o tsv
az storage account network-rule add -g $RG --account-name $ST --vnet-name vnet-app --subnet db --query "virtualNetworkRules[].state" -o tsv
az storage account update -g $RG -n $ST --default-action Deny --query networkRuleSet.defaultAction -o tsv
$SJEKK = "curl -s -m 10 https://$ST.blob.core.windows.net/?comp=list | grep -o -E 'AuthorizationFailure|PublicAccessNotPermitted' || echo ingen kontakt"
"vm-db","vm-web" | ForEach-Object {
  az vm run-command invoke -g $RG -n $_ --command-id RunShellScript --scripts $SJEKK --query "value[0].message" -o tsv
}
az network nic show-effective-route-table -g $RG -n vm-db-nic `
  --query "value[?nextHopType=='VirtualNetworkServiceEndpoint'].{neste:nextHopType, prefikser:length(addressPrefix)}" -o table

Den siste linja viser at service endpointen er ruter på subnettet, til adressene Storage har i regionen.

9. Private endpoint

Hvorfor: en private endpoint er en NIC i ditt subnet med en privat IP for én bestemt ressurs, her blob-delen av storage accounten. Den nås fra VNet-et, fra peerede VNet og fra on-prem, og tjenesten kan stenges helt for internett. Navnet må da slå opp til den private IP-en, og det gjør en private DNS zone, privatelink.blob.core.windows.net. Service endpoint mot private endpoint er et vanlig eksamensspørsmål.

Oppgave: åpne storage accounten og Security + networking → Networking → Private endpoints, og lag pe-blob: sub-resource blob, vnet-app og subnettet web, med integrasjon mot private DNS zone. Kjør nslookup stuke07xxxxxx.blob.core.windows.net på vm-web og lokalt, og sammenlign. Slå så av public network access, og kjør sjekkene fra steg 8 på nytt.

Lokalt går navnet via privatelink til en public IP, og på vm-web til en adresse i 10.7.1.0/24. Etterpå kommer begge VM-ene gjennom, fordi også vm-db slår opp den private IP-en. Lokalt blir du stoppet.

Vis kommando
$SAID = az storage account show -g $RG -n $ST --query id -o tsv
az network private-endpoint create -g $RG -n pe-blob -l $L --vnet-name vnet-app --subnet web --private-connection-resource-id $SAID `
  --group-id blob --connection-name pe-blob --query "customDnsConfigs[0].ipAddresses[0]" -o tsv
az network private-dns zone create -g $RG -n privatelink.blob.core.windows.net --query provisioningState -o tsv
az network private-dns link vnet create -g $RG -z privatelink.blob.core.windows.net -n app --virtual-network vnet-app `
  --registration-enabled false --query provisioningState -o tsv
az network private-endpoint dns-zone-group create -g $RG --endpoint-name pe-blob -n blob `
  --private-dns-zone privatelink.blob.core.windows.net --zone-name blob --query provisioningState -o tsv
az vm run-command invoke -g $RG -n vm-web --command-id RunShellScript --scripts "nslookup $ST.blob.core.windows.net" --query "value[0].message" -o tsv
nslookup "$ST.blob.core.windows.net"
az storage account update -g $RG -n $ST --public-network-access Disabled --query publicNetworkAccess -o tsv

Portalen lager endepunktet, sonen, linken og DNS zone group i én dialog. Det tok rundt to minutter i testen.

Del C — Navneoppslag (ca. 10 min)

10. Private og public DNS zones

Hvorfor: Azure DNS har to typer soner. En private zone gir navn inne i VNet-ene den er linket til, og med autoregistrering legger VM-ene seg inn selv. Et VNet kan ha autoregistrering mot bare én sone, men en sone kan linkes til mange VNet. En public zone er domenet ditt på internett. Azure gir sonen fire navnetjenere, og domenet virker først når registraren peker på dem med NS-poster. En alias-post peker på en Azure-ressurs, som en public IP, og følger med hvis adressen endres. Den kan stå på roten av domenet, der en CNAME ikke er lov.

Oppgave: lag private DNS-sonen uke07.intern. Link den til vnet-app med autoregistrering og til vnet-hub uten. Se postene som kom av seg selv, og kjør nslookup vm-db.uke07.intern; nslookup vm-nva.uke07.intern på vm-nva. Lag så en DNS zone som heter uke07- og verdien av $ID, med .no til slutt. Legg til A-posten www med 203.0.113.10, og en alias-post på @ som peker på pip-web. Slå opp begge mot en av navnetjenerne til sonen.

vm-nva står ikke i sonen, fordi vnet-hub ikke har autoregistrering. Linkene tok rundt ett minutt hver i testen. Domenet er ikke delegert, så uten navnetjeneren finner ikke nslookup det.

Vis kommando
az network private-dns zone create -g $RG -n uke07.intern --query provisioningState -o tsv
az network private-dns link vnet create -g $RG -z uke07.intern -n app --virtual-network vnet-app --registration-enabled true `
  --query provisioningState -o tsv
az network private-dns link vnet create -g $RG -z uke07.intern -n hub --virtual-network vnet-hub --registration-enabled false `
  --query provisioningState -o tsv
az network private-dns record-set a list -g $RG -z uke07.intern --query "[].{navn:name, ip:aRecords[0].ipv4Address, auto:isAutoRegistered}" -o table
az vm run-command invoke -g $RG -n vm-nva --command-id RunShellScript --scripts "nslookup vm-db.uke07.intern; nslookup vm-nva.uke07.intern" `
  --query "value[0].message" -o tsv
$ZONE = "uke07-$ID.no"
az network dns zone create -g $RG -n $ZONE --query nameServers -o tsv
az network dns record-set a add-record -g $RG -z $ZONE -n www -a 203.0.113.10 --query fqdn -o tsv
$PIP = az network public-ip show -g $RG -n pip-web --query id -o tsv
az network dns record-set a create -g $RG -z $ZONE -n "@" --target-resource $PIP --query fqdn -o tsv
az network dns record-set list -g $RG -z $ZONE --query "[].{navn:name, post:type}" -o table
$NS = az network dns zone show -g $RG -n $ZONE --query "nameServers[0]" -o tsv
nslookup "www.$ZONE" $NS
nslookup $ZONE $NS

Roten av sonen har tre poster: NS og SOA, som Azure lager, og aliaset ditt.
