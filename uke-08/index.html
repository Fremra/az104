Står du fast, eller vil du sjekke resultatet, ligger kommandoen under Vis kommando. Tester inne i VM-ene kjører du med run command, som i uke 7. Går tiden fra deg, hopp over steg 4. Fasiten ligger under labben.

Før møtet

Samme oppsett som i uke 2: portalen i et privat vindu med lab-brukeren, og az lokalt med kursprofilen eller i Cloud Shell. Lag en mappe til labben, og sett variablene:

Del A — Lastbalansering (ca. 35 min)

1. Nett og webservere i Bicep

Hvorfor: en load balancer trenger noe å fordele trafikken på. Fila lager to webservere og en klient-VM. Webserverne svarer med navnet sitt, så du ser hvilken som svarte, og klienten tester fra innsiden av VNet-et. Subnettene er private, så VM-ene kommer ikke ut på internett og kan ikke laste ned pakker. Derfor bruker webserveren Python, som allerede finnes i Ubuntu.

Oppgave: lag rg-uke08 i Sweden Central, og deploy fila under. Den lager vnet-uke08 med subnettene web og klient. I web står vm-web1 og vm-web2, og i klient står vm-klient. Subnettet web har NSG-en nsg-web, som bare har standardreglene. VM-ene har ingen public IP og slår seg av kl. 20.

2. Offentlig load balancer

Hvorfor: Azure Load Balancer fordeler nye TCP- og UDP-tilkoblinger mellom VM-ene i en backend pool. Den består av fire deler: en frontend-IP, en backend pool, en health probe som sjekker hvilke VM-er som svarer, og en regel som knytter dem sammen. En offentlig load balancer har en public IP som frontend. Standard er den eneste SKU-en etter at Basic ble faset ut i 2025.

Oppgave: lag load balanceren lb-web med SKU Standard, type Public og tier Regional. Gi den frontend-IP-en fe-web med en ny public IP, pip-lb, og backend poolen web med vm-web1 og vm-web2. Lag regelen http fra port 80 til port 80, med en ny health probe, http, av typen HTTP på port 80 og stien /. Når load balanceren er klar, kjører du linjene under lokalt. 

$LB = az network public-ip show -g $RG -n pip-lb --query ipAddress -o tsv
1..6 | ForEach-Object { try { (Invoke-WebRequest "http://$LB" -UseBasicParsing -DisableKeepAlive -TimeoutSec 5).Content.Trim() } catch { "ingen svar" } }

Alle seks gir ingen svar. Årsaken finner du i steg 3.

Vis kommando
az network public-ip create -g $RG -n pip-lb --sku Standard --query publicIp.ipAddress -o tsv
az network lb create -g $RG -n lb-web --sku Standard --public-ip-address pip-lb --frontend-ip-name fe-web --backend-pool-name web `
  --query loadBalancer.provisioningState -o tsv
az network lb probe create -g $RG --lb-name lb-web -n http --protocol Http --port 80 --path / --query provisioningState -o tsv
az network lb rule create -g $RG --lb-name lb-web -n http --protocol Tcp --frontend-port 80 --backend-port 80 --frontend-ip-name fe-web `
  --backend-pool-name web --probe-name http --disable-outbound-snat true --query provisioningState -o tsv
"vm-web1","vm-web2" | ForEach-Object {
  az network nic ip-config address-pool add -g $RG --nic-name "$_-nic" --ip-config-name ipconfig1 --lb-name lb-web --address-pool web -o none
}

Det tok under ett minutt i testen.

3. Feilsøk load balanceren

Hvorfor: en load balancer med SKU Standard er stengt for trafikk inn til en NSG åpner. Health proben kommer fra Azure-plattformen med service tagen AzureLoadBalancer, og den slipper inn via en standardregel. VM-ene kan derfor være friske i load balanceren selv om klientene blir stoppet. Health probe status er det første du sjekker: en VM som ikke svarer på proben, får ingen nye tilkoblinger.

Oppgave: legg til den innkommende regelen tillat-http i nsg-web, med kilde Internet, port 80, Allow og prioritet 100. Kjør testen fra steg 2 igjen. Stopp så webserveren på vm-web1 med run command og systemctl stop web, og kjør testen enda en gang. Åpne lb-web og Monitoring → Metrics. Velg Health Probe Status, og del opp på Backend IP Address med Apply splitting. Start til slutt webserveren igjen med systemctl start web.

Med regelen svarer begge VM-ene. Når webserveren er stoppet, svarer bare vm-web2, og etter et par minutter viser metrikken at 10.8.1.4 har falt ut.

Vis kommando
az network nsg rule create -g $RG --nsg-name nsg-web -n tillat-http --priority 100 --access Allow --protocol Tcp `
  --source-address-prefixes Internet --destination-port-ranges 80 --query provisioningState -o tsv
az vm run-command invoke -g $RG -n vm-web1 --command-id RunShellScript --scripts "systemctl stop web" --query "value[0].message" -o tsv
$LBID = az network lb show -g $RG -n lb-web --query id -o tsv
az monitor metrics list --resource $LBID --metric DipAvailability --filter "BackendIPAddress eq '*'" --interval PT1M `
  --query "value[0].timeseries[].{ip:metadatavalues[0].value, prosent:data[?average].average | [-1]}" -o table
az vm run-command invoke -g $RG -n vm-web1 --command-id RunShellScript --scripts "systemctl start web" --query "value[0].message" -o tsv

I API-et heter Health Probe Status DipAvailability. Metrikken viser snittet per minutt, så kjør kommandoen gjerne et par ganger.

4. Session persistence

Hvorfor: load balanceren velger VM ut fra en hash av fem verdier: kilde-IP, kildeport, mål-IP, målport og protokoll. Hver ny tilkobling kan derfor havne på en annen VM. Med session persistence satt til Client IP bruker hashen bare kilde- og mål-IP, og samme klient havner på samme VM så lenge den er frisk. Client IP and protocol tar i tillegg med protokollen.

Oppgave: åpne regelen http i lb-web under Settings → Load balancing rules, og sett Session persistence til Client IP. Kjør testen fra steg 2 igjen.

Nå svarer samme VM alle seks gangene. I testen virket endringen med en gang.

Vis kommando
az network lb rule update -g $RG --lb-name lb-web -n http --load-distribution SourceIP --query loadDistribution -o tsv

I API-et heter valgene Default, SourceIP og SourceIPProtocol.

5. Intern load balancer

Hvorfor: en intern load balancer har en privat IP som frontend og nås bare fra VNet-et, fra peerede VNet og fra on-prem. Den står typisk foran et app- eller databaselag som ikke skal nås fra internett. Samme VM kan stå i backend poolen til både en offentlig og en intern load balancer.

Oppgave: lag lb-intern med SKU Standard og type Internal. Frontend-IP-en fe-intern skal stå i subnettet web med den statiske adressen 10.8.1.100. Gi load balanceren backend poolen web med de samme to VM-ene, og regelen og health proben http som i steg 2. Kjør linja under på vm-klient. 

for i in 1 2 3 4 5 6; do curl -s -m 3 http://10.8.1.100; done

I testen svarte samme VM alle seks gangene, og den andre VM-en da vi kjørte linja på nytt.

Vis kommando
az network lb create -g $RG -n lb-intern --sku Standard --vnet-name vnet-uke08 --subnet web --private-ip-address 10.8.1.100 `
  --frontend-ip-name fe-intern --backend-pool-name web --query loadBalancer.provisioningState -o tsv
az network lb probe create -g $RG --lb-name lb-intern -n http --protocol Http --port 80 --path / --query provisioningState -o tsv
az network lb rule create -g $RG --lb-name lb-intern -n http --protocol Tcp --frontend-port 80 --backend-port 80 --frontend-ip-name fe-intern `
  --backend-pool-name web --probe-name http --query provisioningState -o tsv
"vm-web1","vm-web2" | ForEach-Object {
  az network nic ip-config address-pool add -g $RG --nic-name "$_-nic" --ip-config-name ipconfig1 --lb-name lb-intern --address-pool web -o none
}
az vm run-command invoke -g $RG -n vm-klient --command-id RunShellScript --scripts "for i in 1 2 3 4 5 6; do curl -s -m 3 http://10.8.1.100; done" `
  --query "value[0].message" -o tsv

Advarselen om public IP fra den første kommandoen kan du se bort fra. Med --subnet lager den ingen public IP.

Del B — Network Watcher (ca. 25 min)

6. IP flow verify og next hop

Hvorfor: Network Watcher er en samling verktøy for å overvåke og feilsøke nettverk i en region. Den slås på av seg selv når du lager et VNet, og ligger i NetworkWatcherRG. IP flow verify sier om en pakke slipper gjennom NSG-ene til en VM, og hvilken regel som avgjør det. Next hop viser hvor en pakke fra en VM går videre. Sammen skiller de et NSG-problem fra et rutingproblem, uten at du logger inn på VM-en.

Oppgave: åpne Network Watcher → IP flow verify. Test innkommende TCP til vm-web1 på port 80 fra den eksterne adressen 203.0.113.10, port 60000. Bytt så til port 22. Åpne Next hop, og test fra vm-klient til 10.8.1.100 og til 8.8.8.8.

Port 80 slipper inn via tillat-http, mens port 22 stoppes av DenyAllInBound. Next hop er VirtualNetwork til load balanceren og Internet til 8.8.8.8.

Vis kommando
az network watcher test-ip-flow -g $RG --vm vm-web1 --direction Inbound --protocol TCP --local 10.8.1.4:80 --remote 203.0.113.10:60000 -o table
az network watcher test-ip-flow -g $RG --vm vm-web1 --direction Inbound --protocol TCP --local 10.8.1.4:22 --remote 203.0.113.10:60000 -o table
az network watcher show-next-hop -g $RG --vm vm-klient --source-ip 10.8.2.4 --dest-ip 10.8.1.100 -o table
az network watcher show-next-hop -g $RG --vm vm-klient --source-ip 10.8.2.4 --dest-ip 8.8.8.8 -o table

7. Connection troubleshoot og vei ut

Hvorfor: next hop sier Internet, men subnettet er privat, så vm-klient kommer likevel ikke ut. Connection troubleshoot prøver en ekte tilkobling fra VM-en via Network Watcher-agenten og viser om den kommer fram. En NAT gateway gir VM-ene i et subnet en felles, fast adresse ut, uten at de kan nås utenfra. Det er den anbefalte måten å gi et privat subnet tilgang til internett på.

Oppgave: åpne Network Watcher → Connection troubleshoot, og test fra vm-klient til www.microsoft.com på port 443. Lag så NAT gatewayen ng-klient med en ny public IP, pip-ng, og koble den til subnettet klient. Test igjen, og kjør curl -s -m 5 https://ifconfig.me på vm-klient.

Først får du Unreachable og etterpå Reachable, og curl viser IP-en til pip-ng. Hver kjøring av connection troubleshoot tok drøyt ett minutt i testen.

Vis kommando
az network watcher test-connectivity -g $RG --source-resource vm-klient --dest-address www.microsoft.com --dest-port 443 `
  --query "{status:connectionStatus, sendt:probesSent, feilet:probesFailed}" -o table
az network public-ip create -g $RG -n pip-ng --sku Standard --query publicIp.ipAddress -o tsv
az network nat gateway create -g $RG -n ng-klient --public-ip-addresses pip-ng --query provisioningState -o tsv
az network vnet subnet update -g $RG --vnet-name vnet-uke08 -n klient --nat-gateway ng-klient --query natGateway.id -o tsv
az network watcher test-connectivity -g $RG --source-resource vm-klient --dest-address www.microsoft.com --dest-port 443 `
  --query "{status:connectionStatus, sendt:probesSent, feilet:probesFailed}" -o table
az vm run-command invoke -g $RG -n vm-klient --command-id RunShellScript --scripts "curl -s -m 5 https://ifconfig.me" --query "value[0].message" -o tsv

8. Connection monitor

Hvorfor: connection troubleshoot sjekker én gang. Connection monitor tester de samme forbindelsene hele tiden, lagrer resultatene i Log Analytics og kan varsle når en forbindelse faller ut.

Oppgave: åpne Network Watcher → Connection monitor → Create. Kall den cm-uke08, velg Sweden Central, og bruk workspacen log-uke08 i stedet for den som connection monitor ellers lager. Lag testgruppen web med vm-klient som kilde og vm-web1 og www.microsoft.com som mål. Legg til testkonfigurasjonen tcp-80: TCP på port 80 hvert 30. sekund. Når resultatene har kommet, stopper du webserveren på vm-web1 som i steg 3. Se hvordan statusen endrer seg, og start webserveren igjen.

I testen kom de første resultatene etter rundt fire minutter, og feilen mot vm-web1 viste seg to minutter etter at webserveren ble stoppet.

Vis kommando
$WS = az monitor log-analytics workspace show -g $RG -n log-uke08 --query id -o tsv
$KLIENT = az vm show -g $RG -n vm-klient --query id -o tsv
$WEB1 = az vm show -g $RG -n vm-web1 --query id -o tsv
az network watcher connection-monitor create -n cm-uke08 -l $L --test-group-name web `
  --endpoint-source-name vm-klient --endpoint-source-resource-id $KLIENT `
  --endpoint-dest-name vm-web1 --endpoint-dest-resource-id $WEB1 `
  --test-config-name tcp-80 --protocol Tcp --tcp-port 80 --frequency 30 --workspace-ids $WS --query provisioningState -o tsv
az network watcher connection-monitor endpoint add --connection-monitor cm-uke08 -l $L -n microsoft --address www.microsoft.com `
  --dest-test-groups web -o none
$CM = az network watcher connection-monitor show -n cm-uke08 -l $L --query id -o tsv
az monitor metrics list --resource $CM --metric ChecksFailedPercent --filter "DestinationName eq '*'" --interval PT1M `
  --query "value[0].timeseries[].{til:metadatavalues[0].value, feilet:data[?average].average | [-1]}" -o table

ChecksFailedPercent er andelen sjekker som feilet, i prosent.
