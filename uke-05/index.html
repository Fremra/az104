Lab · 60 min

VM-er, scale sets og App Service plan

De tre Learn-modulene har bare én øvelse, så her er en egen lab. Hvert steg er en oppgave du løser i portalen. Står du fast, eller vil du sjekke resultatet, ligger kommandoen under Vis kommando. Del A er en VM i Bicep, del B er drift av den: størrelse, disker, kryptering og flytting, og del C er availability set, scale set og App Service plan. Fasiten ligger under labben.

Før møtet

Samme oppsett som i uke 2: portalen i et privat vindu med lab-brukeren, og az lokalt med kursprofilen eller i Cloud Shell. Lag en mappe til labben, og sett variablene én gang: 

mkdir uke-05
cd uke-05
$RG = "rg-uke05"
$RG2 = "rg-uke05-flytt"
$L = "swedencentral"
$PASSORD = "Az-$([guid]::NewGuid())"

Vi bruker Sweden Central denne uka. Norway East har ingen ledige små VM-størrelser for subscriptionene våre. $PASSORD er et tilfeldig passord til VM-ene. Vi logger ikke inn på dem, så du trenger ikke å huske det. Tjenestene i portalen finner du raskest i søkefeltet øverst.

Del A — VM i Bicep (ca. 15 min)

0. Registrer Microsoft.Compute og encryption at host

Hvorfor: ingen av oss har laget en VM i subscriptionen ennå, så resource provideren for VM-er er ikke registrert. Encryption at host, som vi bruker i steg 6, er en funksjon som må skrus på for subscriptionen før den kan brukes.

Oppgave: dette steget gjør du med az. Registrer featuren først og så provideren, ellers blir ikke featuren med. Står featuren som Registering, går du videre og kjører de to siste linjene igjen før steg 6. 

az feature register --namespace Microsoft.Compute --name EncryptionAtHost --query properties.state -o tsv
az provider register --namespace Microsoft.Compute
az provider show --namespace Microsoft.Compute --query registrationState -o tsv

1. VM i Bicep

Hvorfor: en VM er flere ressurser: selve VM-en, et nettverkskort (NIC), en OS-disk og et VNet. Bicep-fila lager alle sammen, og i tillegg en auto-shutdown-plan som slår av VM-en kl. 20 hver kveld, i tilfelle den blir glemt. VM-en står i availability zone 1 og har ingen offentlig IP.

Oppgave: lag rg-uke05 i Sweden Central, og deploy fila under. Åpne VM-en i portalen, og finn størrelsen, sonen og OS-disken under Overview og tidspunktet under Operations → Auto-shutdown. 

@'
@description('Størrelsen på VM-en')
param vmSize string = 'Standard_D2als_v6'

@description('Brukernavnet til administratoren')
param adminUsername string = 'azureuser'

@secure()
@description('Passordet til administratoren. Vi logger ikke inn, så det trengs bare når VM-en lages')
param adminPassword string

resource vnet 'Microsoft.Network/virtualNetworks@2024-05-01' = {
  name: 'vnet-uke05'
  location: resourceGroup().location
  properties: {
    addressSpace: {
      addressPrefixes: [ '10.5.0.0/16' ]
    }
    subnets: [
      {
        name: 'default'
        properties: {
          addressPrefix: '10.5.0.0/24'
        }
      }
    ]
  }
}

resource nic 'Microsoft.Network/networkInterfaces@2024-05-01' = {
  name: 'vm1-nic'
  location: resourceGroup().location
  properties: {
    ipConfigurations: [
      {
        name: 'ipconfig1'
        properties: {
          subnet: {
            id: '${vnet.id}/subnets/default'
          }
        }
      }
    ]
  }
}

resource vm 'Microsoft.Compute/virtualMachines@2024-07-01' = {
  name: 'vm1'
  location: resourceGroup().location
  zones: [ '1' ]
  properties: {
    hardwareProfile: {
      vmSize: vmSize
    }
    osProfile: {
      computerName: 'vm1'
      adminUsername: adminUsername
      adminPassword: adminPassword
    }
    storageProfile: {
      imageReference: {
        publisher: 'Canonical'
        offer: 'ubuntu-24_04-lts'
        sku: 'server'
        version: 'latest'
      }
      osDisk: {
        name: 'vm1-osdisk'
        createOption: 'FromImage'
        deleteOption: 'Delete'
        managedDisk: {
          storageAccountType: 'StandardSSD_LRS'
        }
      }
    }
    networkProfile: {
      networkInterfaces: [
        {
          id: nic.id
          properties: {
            deleteOption: 'Delete'
          }
        }
      ]
    }
  }
}

resource autoShutdown 'Microsoft.DevTestLab/schedules@2018-09-15' = {
  name: 'shutdown-computevm-vm1'
  location: resourceGroup().location
  properties: {
    status: 'Enabled'
    taskType: 'ComputeVmShutdownTask'
    dailyRecurrence: {
      time: '2000'
    }
    timeZoneId: 'W. Europe Standard Time'
    targetResourceId: vm.id
    notificationSettings: {
      status: 'Disabled'
    }
  }
}
'@ | Set-Content main.bicep -Encoding utf8
az group create --name $RG --location $L --query properties.provisioningState -o tsv
az deployment group what-if -g $RG --template-file main.bicep --parameters adminPassword=$PASSORD
az deployment group create -g $RG --name vm --template-file main.bicep --parameters adminPassword=$PASSORD `
  --query properties.provisioningState -o tsv

Deployen tok under to minutter i testen.

2. Run command

Hvorfor: VM-en har ingen offentlig IP, så du kommer ikke inn med SSH. Run command kjører et skript i VM-en gjennom VM-agenten, uten nettverk og uten passord.

Oppgave: åpne Operations → Run command → RunShellScript, og kjør nproc; free -m; lsblk -d -o NAME,SIZE. Du ser antall vCPU-er, minnet i MB og disken. Svaret kommer etter et halvt minutt. sr0 er en liten virtuell CD som Azure bruker når VM-en settes opp.

Vis kommando
az vm run-command invoke -g $RG -n vm1 --command-id RunShellScript --scripts "nproc; free -m; lsblk -d -o NAME,SIZE" `
  --query "value[0].message" -o tsv

Del B — Drift (ca. 25 min)

3. Bytt størrelse

Hvorfor: størrelsen bestemmer vCPU-er, minne og pris. VM-en starter på nytt når du bytter. Finnes ikke den nye størrelsen på maskinvaren VM-en står på, må du deallokere den først. Kvoten teller vCPU-er per region og per familie, og hos oss er grensen 10 vCPU-er i regionen.

Oppgave: åpne Availability + scale → Size, og se hvilke størrelser du kan velge, uten å lagre. Kjør så what-if med Standard_D2as_v6, som har dobbelt så mye minne, og deploy. Sjekk minnet med Run command igjen. 

az deployment group what-if -g $RG --template-file main.bicep --parameters adminPassword=$PASSORD vmSize=Standard_D2as_v6
az deployment group create -g $RG --name vm --template-file main.bicep `
  --parameters adminPassword=$PASSORD vmSize=Standard_D2as_v6 --query properties.provisioningState -o tsv

Endringen som betyr noe i what-if, er vmSize. Resten er støy.

Vis kommando
az vm list-vm-resize-options -g $RG -n vm1 --query "[?contains(name, '_D2a')].name" -o tsv
az vm run-command invoke -g $RG -n vm1 --command-id RunShellScript --scripts "free -m" --query "value[0].message" -o tsv

4. Datadisk

Hvorfor: OS-disken er til operativsystemet. Data legger du på egne managed disks, som kan kobles til mens VM-en kjører. Disktypen (Standard HDD, Standard SSD, Premium SSD, Premium SSD v2 og Ultra Disk) og størrelsen bestemmer ytelse og pris. En disk kan gjøres større, men aldri mindre. En ny disk må formateres i operativsystemet før den kan brukes.

Oppgave: åpne Settings → Disks, og velg Create and attach a new disk: vm1-data, Standard SSD og 4 GiB. Lagre, og se den nye disken med Run command (lsblk -d -o NAME,SIZE). Gjør den så 8 GiB under Size + performance på disken, og kjør Run command igjen. VM-en kjører hele tiden.

Vis kommando
az vm disk attach -g $RG --vm-name vm1 --name vm1-data --new --size-gb 4 --sku StandardSSD_LRS
az vm run-command invoke -g $RG -n vm1 --command-id RunShellScript --scripts "lsblk -d -o NAME,SIZE" --query "value[0].message" -o tsv
az disk update -g $RG -n vm1-data --size-gb 8 --query diskSizeGB -o tsv
az vm run-command invoke -g $RG -n vm1 --command-id RunShellScript --scripts "lsblk -d -o NAME,SIZE" --query "value[0].message" -o tsv

Disken havner i samme sone som VM-en. En disk i en annen sone kan ikke kobles til.

5. Deallokér

Hvorfor: slår du av VM-en fra operativsystemet, står den som Stopped, og du betaler fortsatt for den. Stop i portalen og az vm deallocate gir Stopped (deallocated), og da betaler du bare for diskene. Noen endringer krever en deallokert VM, som å bytte disktype på en disk som er koblet til.

Oppgave: prøv å bytte vm1-data til Premium SSD under Size + performance mens VM-en kjører. Det går ikke. Stopp VM-en (Stop under Overview), og bytt igjen. La den stå stoppet til steg 6.

Vis kommando
az disk update -g $RG -n vm1-data --sku Premium_LRS --query sku.name -o tsv      # feiler
az vm deallocate -g $RG -n vm1
az disk update -g $RG -n vm1-data --sku Premium_LRS --query sku.name -o tsv

6. Encryption at host

Hvorfor: managed disks er alltid kryptert der de lagres. Encryption at host krypterer i tillegg disk-cachen og den midlertidige disken på serveren VM-en kjører på, så dataene er kryptert hele veien fra VM-en til lagringen. Studieguiden nevner encryption at host i stedet for Azure Disk Encryption, som Microsoft fjerner i 2028. Det kan bare skrus på når VM-en er deallokert.

Oppgave: med VM-en fortsatt stoppet, åpne Settings → Disks → Additional settings, og sett Encryption at host til Yes. Start VM-en, og se at den står som Running.

Vis kommando
az vm update -g $RG -n vm1 --set securityProfile.encryptionAtHost=true --query securityProfile.encryptionAtHost -o tsv
az vm start -g $RG -n vm1
az vm get-instance-view -g $RG -n vm1 --query "instanceView.statuses[1].displayStatus" -o tsv

7. Flytt VM-en

Hvorfor: en VM kan flyttes til en annen resource group eller subscription, men NIC-en og diskene må bli med. Til en annen resource group kan VNet-et bli igjen, til en annen subscription må det også flyttes. Ressurs-id-en endres, så skript og annet som peker på den gamle id-en, må oppdateres. Til en annen region flytter du med Azure Resource Mover, eller du lager VM-en på nytt der. Eksamen spør hva som må flyttes sammen.

Oppgave: lag rg-uke05-flytt. Åpne rg-uke05, merk vm1, vm1-nic, vm1-osdisk, vm1-data og shutdown-computevm-vm1, og velg Move → Move to another resource group. Flyttingen tok fire–fem minutter i testen, og VM-en kjørte hele tiden. Gå videre til del C mens den går.

Vis kommando
az group create --name $RG2 --location $L --query properties.provisioningState -o tsv
$IDER = az resource list -g $RG --query "[?contains(name, 'vm1')].id" -o tsv | ForEach-Object { $_.ToLower() }
az resource move --destination-group $RG2 --ids $IDER
az resource list -g $RG2 --query "[].name" -o tsv

az krever at navnet på resource groupen er skrevet likt i alle id-ene, og OS-disken har det med store bokstaver. Derfor ToLower(). Kommandoen venter til flyttingen er ferdig.

Del C — Tilgjengelighet og skalering (ca. 20 min)

8. Availability set

Hvorfor: et availability set sprer VM-ene i ett datasenter på fault domains (eget rack med strøm og nettverk, høyst 3) og update domains (startes på nytt én om gangen ved vedlikehold, høyst 20). En availability zone er ett eller flere egne datasentre i regionen. SLA-en er 99,95 % med availability set og 99,99 % med VM-er i to eller flere soner. En VM står enten i en sone eller i et availability set, og det velges når VM-en lages. En VM som finnes, kan ikke legges inn i et availability set etterpå.

Oppgave: lag availability setet as-uke05 i rg-uke05 med 2 fault domains og 5 update domains. Lag så vm2 i samme resource group med Create → Virtual machine: availability setet, Ubuntu Server 24.04 LTS, Standard_D2als_v6 og Password med et passord du finner på. Velg vnet-uke05 og None som public IP under Networking, og slå på auto-shutdown under Management. Se til slutt under as-uke05 hvilket fault domain og update domain vm2 fikk.

Vis kommando
az vm availability-set create -g $RG -n as-uke05 --platform-fault-domain-count 2 --platform-update-domain-count 5 `
  --query "{fd:platformFaultDomainCount, ud:platformUpdateDomainCount}" -o json
az network nic create -g $RG -n vm2-nic --vnet-name vnet-uke05 --subnet default --query NewNIC.provisioningState -o tsv
az vm create -g $RG -n vm2 --availability-set as-uke05 --nics vm2-nic --image Ubuntu2404 --size Standard_D2als_v6 `
  --storage-sku StandardSSD_LRS --admin-username azureuser --admin-password $PASSORD --query powerState -o tsv
az vm auto-shutdown -g $RG -n vm2 --time 1900 --query dailyRecurrence.time -o tsv      # UTC, altså kl. 20 her
az vm get-instance-view -g $RG -n vm2 --query "instanceView.{fd:platformFaultDomain, ud:platformUpdateDomain}" -o json

NIC-en lages først, så az vm create ikke lager offentlig IP og NSG.

9. Scale set

Hvorfor: et scale set er en gruppe like VM-er som kan skaleres etter regler. Med Flexible orchestration, som er standard nå, blir instansene vanlige VM-er du ser i resource groupen, og de kan spres på soner. Autoscale har et minimum, et maksimum og et standardantall, og regler for når det skal skaleres ut og inn. Eksamen gir deg gjerne en regel og spør hvor mange instanser du ender med.

Oppgave: deploy fila under. Den gir to instanser i hver sin sone. Åpne vmss-uke05 → Availability + scale → Scaling, og velg Custom autoscale: minimum 1, maksimum 3 og standard 2. Legg til en regel som legger til én instans når CPU er over 70 % i snitt i 5 minutter, og en som fjerner én når den er under 30 %. Lagre, og følg med under Instances. VM-ene gjør ingenting, så etter noen minutter står det én igjen. Maksimum 3 er det kvoten tåler: vm1, vm2 og tre instanser er 10 vCPU-er. 

@'
@description('Brukernavnet til administratoren')
param adminUsername string = 'azureuser'

@secure()
@description('Passordet til administratoren. Vi logger ikke inn, så det trengs bare når instansene lages')
param adminPassword string

resource subnet 'Microsoft.Network/virtualNetworks/subnets@2024-05-01' existing = {
  name: 'vnet-uke05/default'
}

resource vmss 'Microsoft.Compute/virtualMachineScaleSets@2024-07-01' = {
  name: 'vmss-uke05'
  location: resourceGroup().location
  zones: [ '1', '2', '3' ]
  sku: {
    name: 'Standard_D2als_v6'
    capacity: 2
  }
  properties: {
    orchestrationMode: 'Flexible'
    platformFaultDomainCount: 1
    virtualMachineProfile: {
      osProfile: {
        computerNamePrefix: 'vmss'
        adminUsername: adminUsername
        adminPassword: adminPassword
      }
      storageProfile: {
        imageReference: {
          publisher: 'Canonical'
          offer: 'ubuntu-24_04-lts'
          sku: 'server'
          version: 'latest'
        }
        osDisk: {
          createOption: 'FromImage'
          deleteOption: 'Delete'
          managedDisk: {
            storageAccountType: 'StandardSSD_LRS'
          }
        }
      }
      networkProfile: {
        networkApiVersion: '2024-05-01'
        networkInterfaceConfigurations: [
          {
            name: 'nic'
            properties: {
              primary: true
              deleteOption: 'Delete'
              ipConfigurations: [
                {
                  name: 'ipconfig1'
                  properties: {
                    subnet: {
                      id: subnet.id
                    }
                  }
                }
              ]
            }
          }
        ]
      }
    }
  }
}
'@ | Set-Content vmss.bicep -Encoding utf8
az deployment group create -g $RG --name vmss --template-file vmss.bicep --parameters adminPassword=$PASSORD `
  --query properties.provisioningState -o tsv
Vis kommando
az vm list -g $RG --query "[?contains(name, 'vmss')].{navn:name, sone:zones[0]}" -o table
$VMSS = az vmss show -g $RG -n vmss-uke05 --query id -o tsv
az monitor autoscale create -g $RG --resource $VMSS --name skaler-vmss --min-count 1 --max-count 3 --count 2 -o none
az monitor autoscale rule create -g $RG --autoscale-name skaler-vmss --condition "Percentage CPU > 70 avg 5m" --scale out 1 -o none
az monitor autoscale rule create -g $RG --autoscale-name skaler-vmss --condition "Percentage CPU < 30 avg 5m" --scale in 1 -o none
az vmss show -g $RG -n vmss-uke05 --query sku.capacity -o tsv      # kjør igjen etter noen minutter

10. App Service plan

Hvorfor: en App Service plan er maskinene web-appene kjører på, og alle appene i planen deler dem. Tieren bestemmer hva du får: Free og Shared kan ikke skaleres ut, Basic kan skaleres manuelt til 3 instanser, Standard til 10 med autoscale, og Premium til 30. Scale up er en større tier, scale out er flere instanser. Selve App Service tar vi i uke 6.

Oppgave: lag en Linux-plan plan-uke05 i rg-uke05 med Basic B1 (søk etter App Service plans). Skaler ut til 2 instanser under Scale out, og se hvor høyt du kan gå. Skaler så opp til Standard S1 under Scale up, og se at Scale out nå går til 10 og har regelbasert autoscale.

Vis kommando
az appservice plan create -g $RG -n plan-uke05 --sku B1 --is-linux --query sku.name -o tsv
az appservice plan update -g $RG -n plan-uke05 --number-of-workers 2 --query sku.capacity -o tsv
az appservice plan update -g $RG -n plan-uke05 --number-of-workers 4 --query sku.capacity -o tsv      # feiler
az appservice plan update -g $RG -n plan-uke05 --sku S1 --query sku.name -o tsv

Opprydding

Autoscale, auto-shutdown og diskene forsvinner sammen med resource groupene. Slett rg-uke05-flytt først. NIC-en til vm1 bruker VNet-et i rg-uke05, og VNet-et kan ikke slettes før NIC-en er borte. Første linje venter til gruppen er slettet, og det tok et par minutter i testen. 

az group delete --name $RG2 --yes
az group delete --name $RG --yes --no-wait

Sjekk etter et par minutter at ingenting står igjen:

az group list -o table

NetworkWatcherRG lages av seg selv sammen med det første VNet-et i en region. Den er gratis og kan stå, det samme kan featuren og resource provideren.
