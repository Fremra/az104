Storage account, tilgang og Azure Files

De fire Learn-modulene har bare to øvelser, så her er en egen lab. Hvert steg er en oppgave du løser i portalen. Står du fast, eller vil du sjekke resultatet, ligger kommandoen under Vis kommando. Fasiten ligger under labben.

Før møtet

Samme oppsett som i uke 2: portalen i et privat vindu med lab-brukeren, og az lokalt med kursprofilen eller i Cloud Shell. Lag en mappe til labben, sett variabelen én gang, og lag en liten fil til opplastingene:

Del A — Storage account (ca. 15 min)

1. Storage account i Bicep

Hvorfor: navnet på en storage account blir en del av URL-en, så det må være unikt i hele Azure. Det kan ha 3–24 tegn, bare små bokstaver og tall, og ingen bindestrek. Bicep-fila lager navnet med uniqueString, så alle får hvert sitt. StorageV2 (general-purpose v2) er standardtypen og den eksamen forventer at du velger.

Oppgave: lag rg-uke04 i Norway East, og deploy fila under. Åpne storage accounten i portalen og finn redundansen og access tier under Overview. 

@'
@description('Redundansen til storage accounten')
@allowed([
  'Standard_LRS'
  'Standard_GRS'
  'Standard_RAGRS'
  'Standard_ZRS'
])
param skuName string = 'Standard_LRS'

@description('Soft delete: slettede blober, containere og filshare kan hentes tilbake i 7 dager')
param softDelete bool = false

@description('Versjonering: gamle versjoner av en blob tas vare på når den skrives over')
param versjonering bool = false

resource sa 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'st${uniqueString(resourceGroup().id)}'
  location: resourceGroup().location
  sku: {
    name: skuName
  }
  kind: 'StorageV2'
  properties: {
    accessTier: 'Hot'
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
}

resource blob 'Microsoft.Storage/storageAccounts/blobServices@2023-05-01' = {
  parent: sa
  name: 'default'
  properties: {
    isVersioningEnabled: versjonering
    deleteRetentionPolicy: {
      enabled: softDelete
      days: softDelete ? 7 : null
    }
    containerDeleteRetentionPolicy: {
      enabled: softDelete
      days: softDelete ? 7 : null
    }
  }
}

resource filer 'Microsoft.Storage/storageAccounts/fileServices@2023-05-01' = {
  parent: sa
  name: 'default'
  properties: {
    shareDeleteRetentionPolicy: {
      enabled: softDelete
      days: softDelete ? 7 : null
    }
  }
}

output navn string = sa.name
'@ | Set-Content main.bicep -Encoding utf8
az group create --name $RG --location norwayeast --query properties.provisioningState -o tsv
az deployment group what-if -g $RG --template-file main.bicep
az deployment group create -g $RG --name storage --template-file main.bicep --query properties.provisioningState -o tsv
$SA = az deployment group show -g $RG --name storage --query properties.outputs.navn.value -o tsv
$SA

$SA er navnet på storage accounten, og det brukes i resten av labben.

2. Bytt redundans

Hvorfor: LRS har tre kopier i ett datasenter, ZRS fordeler dem på tre availability zones, og GRS kopierer i tillegg til regionen som er paret med din, så GRS har seks kopier. Norway East er paret med Norway West. RA-GRS lar deg også lese fra den kopien. Til ZRS må accounten konverteres, og det tar tid. Det spør eksamen om.

Oppgave: åpne Data management → Redundancy, og se hvilke valg du har, uten å lagre. Kjør så what-if med Standard_GRS. Den viser endringen uten å gjøre den. 

az deployment group what-if -g $RG --template-file main.bicep --parameters skuName=Standard_GRS
Ikke lagre endringen til GRS. Mens kopien til Norway West settes opp, kan ikke accounten slettes, og i testen sto den slik i en halvtime.

3. Owner er ikke nok

Hvorfor: Owner styrer storage accounten (control plane), men gir ikke tilgang til dataene i den (data plane). For å lese og skrive blober med Entra-brukeren din trenger du en egen rolle, som Storage Blob Data Contributor. Det er et av de vanligste eksamensspørsmålene om storage.

Oppgave: dette steget gjør du med az, fordi portalen bruker nøkkelen i det stille. Lag containeren dokumenter, og prøv å laste opp hei.txt med Entra-brukeren din. Containeren går, men opplastingen feiler. Gi deg selv rollen, og prøv igjen. I testen tok det fra 16 sekunder til et par minutter før rollen virket, så feiler den fortsatt, vent litt og kjør linjen på nytt. 

az storage container create --account-name $SA --name dokumenter --auth-mode login
az storage blob upload --account-name $SA -c dokumenter -n hei.txt -f hei.txt --auth-mode login --no-progress --query etag -o tsv      # feiler
$SAID = az storage account show -n $SA --query id -o tsv
$MEG = az ad signed-in-user show --query id -o tsv
az role assignment create --assignee $MEG --role "Storage Blob Data Contributor" --scope $SAID --query roleDefinitionName -o tsv
az storage blob upload --account-name $SA -c dokumenter -n hei.txt -f hei.txt --auth-mode login --no-progress --overwrite --query etag -o tsv

I portalen ser du det samme under containeren: bytt Authentication method fra Access key til Microsoft Entra user account.

4. Access tiers

Hvorfor: Hot, Cool, Cold og Archive koster mindre å lagre og mer å lese, jo lenger ned du går. Cool har minstetid 30 dager, Cold 90 og Archive 180. Sletter du før, betaler du likevel for resten. Archive er offline: bloben må hentes tilbake (rehydrate) før den kan leses, og det kan ta opptil 15 timer.

Oppgave: last opp hei.txt en gang til som rapport.txt. Sett den til Cool og så Archive (Change tier på bloben), og prøv å laste den ned. Det feiler. Sett den tilbake til Hot, og se at den står som rehydrate-pending-to-hot.

Vis kommando
az storage blob upload --account-name $SA -c dokumenter -n rapport.txt -f hei.txt --auth-mode login --no-progress --query etag -o tsv
az storage blob set-tier --account-name $SA -c dokumenter -n rapport.txt --tier Cool --auth-mode login
az storage blob set-tier --account-name $SA -c dokumenter -n rapport.txt --tier Archive --auth-mode login
az storage blob download --account-name $SA -c dokumenter -n rapport.txt -f ut.txt --auth-mode login      # BlobArchived
az storage blob set-tier --account-name $SA -c dokumenter -n rapport.txt --tier Hot --rehydrate-priority Standard --auth-mode login
az storage blob show --account-name $SA -c dokumenter -n rapport.txt --auth-mode login `
  --query "{tier:properties.blobTier, status:properties.rehydrationStatus}" -o json

Del B — Tilgang og kryptering (ca. 30 min)

5. Access keys

Hvorfor: en access key gir full tilgang til alt i storage accounten, uten roller. Det er to nøkler, så du kan rotere den ene mens appene bruker den andre. Den som kan liste nøklene, har i praksis tilgang til dataene. I drift legger du nøklene i Key Vault, som kan rotere dem for deg. Det er Microsofts anbefaling.

Oppgave: åpne Security + networking → Access keys, og vis nøklene. Roter key2 (Rotate key). Nøkkel 1 bruker vi i steg 6, så la den stå.

Vis kommando
az storage account keys list -n $SA --query "[].keyName" -o tsv
az storage account keys renew -n $SA -g $RG --key key2 --query "[].keyName" -o tsv
$KEY = az storage account keys list -n $SA --query "[0].value" -o tsv

6. SAS med stored access policy

Hvorfor: en SAS er en lenke med begrenset tilgang og utløpstid. En vanlig SAS signeres med nøkkelen og kan bare trekkes tilbake ved å rotere nøkkelen, og da slutter alle andre SAS-er signert med den også å virke. Knytter du SAS-en til en stored access policy på containeren, trekker du den tilbake ved å slette policyen. En container kan ha fem slike policyer.

Oppgave: lag en stored access policy les på dokumenter med lesetilgang i ett døgn (Access policy på containeren). Lag en SAS for hei.txt som bruker policyen, og åpne URL-en i nettleseren. Slett så policyen, vent et halvt minutt, og last siden på nytt. Nå får du 403.

Vis kommando
$UTLOP = (Get-Date).ToUniversalTime().AddDays(1).ToString("yyyy-MM-ddTHH:mmZ")
az storage container policy create --account-name $SA --account-key $KEY -c dokumenter -n les --permissions r --expiry $UTLOP -o none
$SAS = az storage blob generate-sas --account-name $SA --account-key $KEY -c dokumenter -n hei.txt --policy-name les -o tsv
$URL = "https://$SA.blob.core.windows.net/dokumenter/hei.txt?$SAS"
(Invoke-WebRequest $URL -UseBasicParsing).Content
az storage container policy delete --account-name $SA --account-key $KEY -c dokumenter -n les -o none
(Invoke-WebRequest $URL -UseBasicParsing).Content      # 403 etter ca. 30 s

Se på SAS-en. Den har bare si=les og ingen utløpstid, fordi det står i policyen.

7. User delegation SAS

Hvorfor: en user delegation SAS signeres med Entra-brukeren din i stedet for nøkkelen. Microsoft anbefaler den. Den virker bare for blober, varer høyst sju dager, og gir aldri mer enn rollen din tillater. Alle trekkes tilbake på én gang ved å fornye user delegation-nøklene.

Oppgave: lag en SAS for hei.txt med lesetilgang i to timer, og velg User delegation key som Signing method (Generate SAS på bloben). Åpne URL-en. Trekk den tilbake med kommandoen under, og prøv igjen etter et halvt minutt. 

az storage account revoke-delegation-keys -n $SA -g $RG -o none
Vis kommando
$UTLOP = (Get-Date).ToUniversalTime().AddHours(2).ToString("yyyy-MM-ddTHH:mmZ")
$SAS = az storage blob generate-sas --account-name $SA -c dokumenter -n hei.txt --permissions r --expiry $UTLOP --auth-mode login --as-user -o tsv
$URL = "https://$SA.blob.core.windows.net/dokumenter/hei.txt?$SAS"
(Invoke-WebRequest $URL -UseBasicParsing).Content
az storage account revoke-delegation-keys -n $SA -g $RG -o none
(Invoke-WebRequest $URL -UseBasicParsing).Content      # 403 etter ca. 30 s

8. Brannmur

Hvorfor: brannmuren styrer hvilke nettverk som når dataene. Med Deny som standard slipper bare IP-ene og VNet-ene du har lagt til, inn. Den gjelder data plane: du kan fortsatt administrere accounten. Service endpoints og private endpoints kommer i uke 7.

Oppgave: åpne Security + networking → Networking, og velg Enable from selected networks uten å legge til noe. Prøv å liste blobene. Det feiler. Legg så til din egen IP (Add your client IP address), og prøv igjen etter et halvt minutt.

Vis kommando
az storage account update -n $SA -g $RG --default-action Deny --query networkRuleSet.defaultAction -o tsv
az storage blob list --account-name $SA -c dokumenter --auth-mode login --query "[].name" -o tsv      # feiler etter ca. 30 s
$IP = Invoke-RestMethod https://api.ipify.org
az storage account network-rule add -n $SA -g $RG --ip-address $IP --query "ipRules[].ipAddressOrRange" -o tsv
az storage blob list --account-name $SA -c dokumenter --auth-mode login --query "[].name" -o tsv

Bruker du Cloud Shell, er det Cloud Shell sin IP som må inn, ikke din.

9. Kryptering

Hvorfor: alt i en storage account krypteres alltid med AES-256, og det kan ikke skrus av. Du velger bare hvem som eier nøkkelen: Microsoft (standard) eller deg, med en customer-managed key i Key Vault. Da må Key Vault ha soft delete og purge protection, og storage accounten bruker en managed identity til å hente nøkkelen. Infrastructure encryption (dobbel kryptering) kan bare skrus på når accounten lages. Et encryption scope gir en egen nøkkel til én container eller blob.

Oppgave: åpne Security + networking → Encryption, og se på valgene for nøkkel uten å lagre. Lag så encryption scopet eget med Microsoft-nøkkel (Encryption scopes → Add), og en container hemmelig som bruker det for alle blober. Last opp hei.txt dit, og se hvilket scope bloben har.

Vis kommando
az storage account show -n $SA --query "encryption.{nokkel:keySource, infrastruktur:requireInfrastructureEncryption}" -o json
az storage account encryption-scope create --account-name $SA -g $RG -n eget --key-source Microsoft.Storage --query state -o tsv
az storage container create --account-name $SA --name hemmelig --default-encryption-scope eget `
  --prevent-encryption-scope-override true --auth-mode login
az storage blob upload --account-name $SA -c hemmelig -n hei.txt -f hei.txt --auth-mode login --no-progress --query etag -o tsv
az storage blob show --account-name $SA -c hemmelig -n hei.txt --auth-mode login --query encryptionScope -o tsv

Vi lager ikke en customer-managed key. Key Vault med purge protection kan ikke slettes før det er gått minst sju dager, så den ville blitt stående etter møtet.

Del C — Data og Azure Files (ca. 25 min)

10. Soft delete

Hvorfor: soft delete holder på slettede blober, containere og filshare i 1–365 dager, så de kan hentes tilbake. Det skrus på hver for seg. Parameteren i Bicep-fila skrur på alle tre.

Oppgave: skru på soft delete ved å deploye main.bicep igjen med softDelete=true. Slett hei.txt, vis slettede blober (Show deleted blobs), og hent den tilbake (Undelete). 

az deployment group create -g $RG --name storage --template-file main.bicep `
  --parameters softDelete=true --query properties.provisioningState -o tsv
Vis kommando
az storage blob delete --account-name $SA -c dokumenter -n hei.txt --auth-mode login
az storage blob list --account-name $SA -c dokumenter --include d --auth-mode login --query "[].{navn:name, slettet:deleted}" -o table
az storage blob undelete --account-name $SA -c dokumenter -n hei.txt --auth-mode login -o none
az storage blob list --account-name $SA -c dokumenter --auth-mode login --query "[].name" -o tsv

11. Versjonering

Hvorfor: versjonering tar vare på den gamle versjonen hver gang en blob skrives over eller slettes. Soft delete beskytter mot sletting, versjonering også mot overskriving. Objektreplikering i steg 15 krever versjonering.

Oppgave: deploy fila igjen med versjonering=true. Ta med softDelete=true, ellers skrus soft delete av igjen: det som ikke står i deployen, får standardverdien. Endre hei.txt og last den opp på nytt. Se versjonene under Versions på bloben, og gjør den gamle til gjeldende igjen (Make current version). 

az deployment group create -g $RG --name storage --template-file main.bicep `
  --parameters softDelete=true versjonering=true --query properties.provisioningState -o tsv
Vis kommando
"versjon 2" | Set-Content hei.txt
az storage blob upload --account-name $SA -c dokumenter -n hei.txt -f hei.txt --auth-mode login --no-progress --overwrite --query etag -o tsv
az storage blob list --account-name $SA -c dokumenter --include v --auth-mode login `
  --query "[?name=='hei.txt'].{versjon:versionId, gjeldende:isCurrentVersion}" -o table
$V = az storage blob list --account-name $SA -c dokumenter --include v --auth-mode login `
  --query "[?name=='hei.txt' && !isCurrentVersion].versionId | [0]" -o tsv
az storage blob download --account-name $SA -c dokumenter -n hei.txt --version-id $V -f gammel.txt --auth-mode login --no-progress -o none
az storage blob upload --account-name $SA -c dokumenter -n hei.txt -f gammel.txt --auth-mode login --no-progress --overwrite --query etag -o tsv
az storage blob download --account-name $SA -c dokumenter -n hei.txt -f ut.txt --auth-mode login --no-progress -o none
Get-Content ut.txt

Med az henter du den gamle versjonen og laster den opp igjen. Da blir også «versjon 2» en egen versjon.

12. Lifecycle management

Hvorfor: en lifecycle-regel flytter blober til en billigere tier eller sletter dem etter et antall dager. Regelen kjøres én gang i døgnet, så du ser ikke effekten i møtet. Eksamen gir deg gjerne en regel og spør hva som skjer med en gitt blob.

Oppgave: lag en regel under Data management → Lifecycle management for blober under dokumenter/logg/: Cool etter 30 dager, Archive etter 90 og slett etter 365. Med az er regelen en JSON-fil. 

@'
{
  "rules": [
    {
      "name": "kald-og-slett",
      "enabled": true,
      "type": "Lifecycle",
      "definition": {
        "filters": {
          "blobTypes": [ "blockBlob" ],
          "prefixMatch": [ "dokumenter/logg/" ]
        },
        "actions": {
          "baseBlob": {
            "tierToCool": { "daysAfterModificationGreaterThan": 30 },
            "tierToArchive": { "daysAfterModificationGreaterThan": 90 },
            "delete": { "daysAfterModificationGreaterThan": 365 }
          }
        }
      }
    }
  ]
}
'@ | Set-Content livssyklus.json -Encoding utf8
az storage account management-policy create --account-name $SA -g $RG --policy "@livssyklus.json" --query "policy.rules[].name" -o tsv

@ i starten betyr at az leser fila. Anførselstegnene trengs i PowerShell.

13. Azure Files

Hvorfor: Azure Files er filshare over SMB (port 445) eller NFS. En share har en kvote, og et snapshot tar vare på hele sharen slik den var. Snapshotet er skrivebeskyttet, og du kan hente enkeltfiler fra det. Soft delete for filshare skrudde du på i steg 10. Mange nettverk og internettleverandører stenger port 445, og da kan du ikke mounte sharen. Eksamen spør om det.

Oppgave: lag sharen felles med kvote 10 GiB, last opp hei.txt, og ta et snapshot (Snapshots → Add snapshot). Trykk Connect på sharen og se på skriptet, men ikke kjør det. Sjekk heller om port 445 er åpen herfra. I testen var den stengt. Slett til slutt sharen, og finn den under File shares → Show deleted shares. Undelete virket ikke før det var gått over ti minutter i testen, så det venter vi ikke på.

Vis kommando
az storage share-rm create --storage-account $SA -g $RG --name felles --quota 10 --query shareQuota -o tsv
az storage file upload --account-name $SA --account-key $KEY --share-name felles --source hei.txt --no-progress -o none
az storage share-rm snapshot --storage-account $SA -g $RG --name felles --query snapshotTime -o tsv
Test-NetConnection "$SA.file.core.windows.net" -Port 445 -InformationLevel Quiet      # lokalt
Test-Connection "$SA.file.core.windows.net" -TcpPort 445 -Quiet                       # Cloud Shell
az storage share-rm delete --storage-account $SA -g $RG --name felles --include snapshots --yes
az storage share-rm list --storage-account $SA -g $RG --include-deleted --query "[].{navn:name, slettet:deleted}" -o table

Filen lastes opp med nøkkelen. Med Entra-brukeren trenger du en egen rolle for Azure Files, akkurat som for blober.

14. Entra-tilgang til Azure Files

Hvorfor: når brukere mounter en share over SMB med egen identitet, styres tilgangen i to lag. RBAC på sharen (Storage File Data SMB Share Reader, Contributor og Elevated Contributor) bestemmer om de kommer inn, og NTFS-rettigheter bestemmer hva de får gjøre med mapper og filer. Det krever en identitetskilde: AD DS, Microsoft Entra Domain Services eller Microsoft Entra Kerberos. Med en default share-level permission gjelder én rolle alle brukere. Utenom SMB, i portalen og med az, gir rollen Storage File Data Privileged Contributor tilgang med Entra, slik du gjorde for blober i steg 3.

Oppgave: åpne Data storage → File shares, og se på valgene under Identity-based access uten å sette opp noe. SMB-delen krever en domene- eller Entra-tilknyttet maskin og port 445, og det har vi ikke. Lag så sharen team, og last opp hei.txt med Entra-brukeren din. Det feiler. Gi deg selv rollen, og prøv igjen etter et par minutter. 

az storage share-rm create --storage-account $SA -g $RG --name team --quota 1 --query name -o tsv
az storage file upload --account-name $SA --share-name team --source hei.txt --auth-mode login `
  --enable-file-backup-request-intent --no-progress -o none      # feiler
az role assignment create --assignee $MEG --role "Storage File Data Privileged Contributor" --scope $SAID --query roleDefinitionName -o tsv
az storage file upload --account-name $SA --share-name team --source hei.txt --auth-mode login `
  --enable-file-backup-request-intent --no-progress -o none
az storage file list --account-name $SA --share-name team --auth-mode login --enable-file-backup-request-intent --query "[].name" -o tsv

--enable-file-backup-request-intent må med når du bruker Entra mot Azure Files med az. Rollen går forbi NTFS-rettighetene, derav Privileged.

15. Objektreplikering (valgfritt)

Valgfritt, og det tar tid. Du trenger en storage account til, og kopieringen går i bakgrunnen. Ta steget hvis du er ferdig med resten, og la det gå mens vi går videre.

Hvorfor: objektreplikering kopierer blober asynkront fra en container til en container i en annen storage account, gjerne i en annen region. Begge accountene må ha versjonering, og kilden må ha change feed. Snapshots og blober i Archive blir ikke kopiert. Eksamen spør om kravene.

Oppgave: lag en storage account til i rg-uke04 med versjonering og containeren kopi. Skru på change feed i den første accounten (Data management → Data protection). Lag så en regel fra dokumenter til kopi under Data management → Object replication på den første accounten, og velg Copy over: Everything. Last opp en ny blob, og se etter den i kopi.

Vis kommando
$SA2 = "$($SA)kopi"
az storage account create -n $SA2 -g $RG -l norwayeast --sku Standard_LRS --kind StorageV2 `
  --allow-blob-public-access false --min-tls-version TLS1_2 --query provisioningState -o tsv
az storage account blob-service-properties update -n $SA2 -g $RG --enable-versioning true --query isVersioningEnabled -o tsv
az storage container create --account-name $SA2 --name kopi --auth-mode login
az storage account blob-service-properties update -n $SA -g $RG --enable-change-feed true --query changeFeed.enabled -o tsv
az storage account or-policy create --account-name $SA2 -g $RG --source-account $SA --destination-account $SA2 `
  --source-container dokumenter --destination-container kopi --min-creation-time 1601-01-01T00:00:00Z `
  --query policyId -o tsv
$OR = az storage account or-policy list --account-name $SA2 -g $RG --query "[0].policyId" -o tsv
az storage account or-policy show --account-name $SA2 -g $RG --policy-id $OR | Set-Content or-policy.json
az storage account or-policy create --account-name $SA -g $RG --policy "@or-policy.json" --query policyId -o tsv
"replikert" | Set-Content ny.txt
az storage blob upload --account-name $SA -c dokumenter -n ny.txt -f ny.txt --auth-mode login --no-progress --query etag -o tsv
az storage blob list --account-name $SA2 -c kopi --auth-mode key --query "[].name" -o tsv      # kjør igjen til ny.txt dukker opp

Regelen lages først på målet og så på kilden med samme id. Portalen gjør begge deler for deg. Bloben i kopi leses med nøkkelen, fordi rollen din bare gjelder den første accounten.
